# v1.1 code review (Day 10, 2026-10-12)

A read-only review of the whole repo at `e1403a1` against CLAUDE.md's Clean Code and real-time rules. No code was changed. Each item gives where it is, which rule it touches, why it matters and a suggested fix. Effort is a rough estimate.

**Priorities:** P0 breaks a non-negotiable rule or ships a bug · P1 do first in v1.1, or consider before launch · P2 worthwhile · P3 tidy-up.

## Summary

- **No P0 found.** The audio path follows the real-time rules:
  - `processBlock` and everything it calls does no allocation, takes no locks, does no I/O or logging, and makes no UI calls.
  - `juce::ScopedNoDenormals` is in place.
  - `prepareToPlay` resets every DSP stage and the chunk gains.
  - Latency is reported as 0. citySize is smoothed over 30 ms and bypass crossfades over 20 ms.
  - The bypass parameter is exposed through `getBypassParameter()`.
  - All parameters live in one APVTS, and state goes through it.
- **The largest open issue is UI CPU while automation moves the knob with the editor open** (P1-1).
- **Two CLAUDE.md test requirements are only partly met:** state restore isn't tested at all (P1-2), and the sample-rate and buffer-size coverage stops short of 192 kHz and odd sizes (P1-3).
- **The Clean Code findings are small duplications and a few constants outside their home files** (P2 and P3).

## P1

### P1-1 · UI CPU while the knob moves with the editor open
- **Where:** the editor as a whole: `CityKnob` repaints, `Skyline::setState`/`paint`, `SevenSegmentReadout`.
- **Rule:** CLAUDE.md "In any conflict, real-time audio performance … come first"; definition of done #4.
- **Finding:** in the CPU benchmark (`Tests/CpuBenchmark.cpp`; 30 instances, 128-sample buffer, City size sweeping), an open editor adds about 24–34% of one core. About 6% of that is the benchmark host's own window and loop.
  - Per component: knob 14.4% (before the 60 Hz cap), skyline 6.7%, readout 5.4%.
  - Most of the cost is macOS (Core Animation) redrawing and compositing each repaint, not BigCity's paint code (about 3%).
  - Already tried on Day 10:
    - The 60 Hz knob cap is merged.
    - Opaque components: no gain.
    - Confining repaints: already the case.
    - A shared 60 Hz tick: no clear win, kept on `wip/shared-tick`.
  - Measurements drifted ±10% between runs on the same build.
- **Next:**
  1. Measure in Live: Activity Monitor with automation sweeping, window open against closed. This decides whether more work is needed.
  2. If it's needed, try lowering the skyline and readout rate to 15 Hz while the value moves (a spec change).
  3. Skip renderer or build-setting changes before launch (decided Day 10).
- **Effort:** 15 min to measure; 1–2 h for any fix.

### P1-2 · State restore isn't tested, and non-finite values aren't rejected
- **Where:** `Source/PluginProcessor.cpp:247` (`setStateInformation`).
- **Rule:** CLAUDE.md "Handle invalid states at the boundary (text entry, state restore)".
- **Finding:** restore checks the XML tag, and the APVTS clamps values to each parameter's range. Nothing tests:
  - a wrong tag,
  - truncated data,
  - a missing parameter,
  - an out-of-range value,
  - a non-numeric or `nan` value.

  If a `nan` ever reached `citySizeValue`, `juce::jlimit` would pass it through `CityMacro::map` and `AutoGain::gainDbFor`, and the output would be NaN. I haven't verified whether JUCE's restore path can produce one. That's the first thing the test should establish.
- **Fix:** add `ProcessorTests` cases for each bad-state shape above. If `nan` gets through, make values finite at the boundary, either in `setStateInformation` or with a `std::isfinite` guard where `renderBlock` loads citySize.
- **Effort:** 45 min.
- **Done (Day 10):** `nan` did get through: a saved `"nan"` made City size NaN and the output NaN. `setStateInformation` now drops any non-finite saved value, so that parameter resets to its default, as JUCE does for a parameter missing from the state. `inf` was already clamped, and text that isn't a number reads as 0. Tested: round trip, another plugin's tag, truncated data, header only, random bytes, empty, a missing parameter, out of range, and `nan`/`inf`/non-numeric restored during playback.

### P1-3 · Sample-rate and buffer-size coverage stops short of the CLAUDE.md range
- **Where:** `Tests/ProcessorTests.cpp:103` (null test at 44.1, 48 and 96 kHz); the bypass tests use a fixed 256-sample block.
- **Rule:** CLAUDE.md "Handle any buffer size and sample rates from 44.1 to 192 kHz".
- **Finding:**
  - 88.2, 176.4 and 192 kHz are never run.
  - Nothing uses a block that isn't a multiple of the 32-sample control interval (`SoundSpec::controlIntervalSamples`), such as 1, 31, 33 or 4097, or a block that changes size between calls, as hosts do in automation and offline bounce.
  - The code handles all of these by design; the chunk loop clamps the last chunk. But the definition of done relies on it and nothing checks it.
- **Fix:** extend the null test to 192 kHz, and run null and bypass tests with block sizes { 1, 31, 33, 4097, varying }.
- **Effort:** 30 min.
- **Done (Day 10):** the null and bypass tests run at 44.1, 48, 88.2, 96, 176.4 and 192 kHz with blocks of 1, 7, 31, 33, 511 and 4097 samples, and a varying sequence that includes an empty block. All pass; the null is exact (−inf dB) everywhere.

### P1-4 · Knob and switch have no accessibility handler (D-24)
- **Where:** `Source/CityKnob.h`, `Source/BypassSwitch.h`.
- **Rule:** decision D-24 deferred this to "Saturday cleanup", with v1.1 as the fallback. It hasn't been done.
- **Finding:** VoiceOver can't read or set City size or bypass, because the custom components lost `juce::Slider`'s built-in support.
- **Fix:** `createAccessibilityHandler()` with a value interface (0–100, title "City size") on the knob and a toggle on the switch.
- **Effort:** 45 min, plus a VoiceOver check.

## P2

### P2-1 · The same parameter-write logic appears in three components
- **Where:**

  - `SevenSegmentReadout.cpp:114` (`sendToHost`)
  - `BypassSwitch.cpp:57`
- **Rule:** CLAUDE.md "No duplication".
- **Finding:** "convert to normalised, skip if unchanged, then begin, set and end the gesture" is written out four times, with two near-identical `sendToHost` functions.
- **Fix:** one small helper, for example `ParameterEdit::setWithGesture (parameter, normalised)` plus `isUnchanged`. Keep the knob's drag gesture separate, since it spans many sets.
- **Effort:** 30 min (the tests already cover all four callers).

### P2-2 · The citySize clamp is written six times
- **Where:**
  - `KnobInput.cpp:7`
  - `SevenSegment.cpp:103`
  - `AutoGain.cpp:12`
  - `ReadoutEntry.cpp:75`
  - `SkylineMorph.cpp:9`
  - `CityMacro.cpp:29`
- **Rule:** CLAUDE.md "No duplication".
- **Fix:** `SoundSpec::clampCitySize (float)` as a `constexpr` function next to the range constants, and use it everywhere.
- **Effort:** 20 min.

### P2-3 · Shelf, detune and gain math is redone every 32 samples even when nothing moves
- **Where:** `PluginProcessor.cpp:140` → `applyCitySize`:
  - `AirShelf::update` (RBJ design: `pow`, `sin`, `cos` and `sqrt`)
  - `ShiftVoice::setPitchCents` (two `pow` calls)
  - two `decibelsToGain` calls
- **Rule:** CLAUDE.md "real-time audio performance … come first".
- **Finding:** with the knob still, which is the common case, all of this runs about 1,500 times a second per instance at 48 kHz for no change. It's a share of the 0.82% per instance measured on Day 10.
- **Fix:** skip `applyCitySize` while `citySizeSmoothed` isn't smoothing and the target hasn't changed. Run it once more on the chunk where smoothing ends. The null test and the bypass tests cover it. Benchmark before and after.
- **Effort:** 30 min, plus a benchmark.

### P2-4 · Per-sample `std::sin` in the micro-shift
- **Where:**
  - `MicroShifter.cpp:66`: the sin² fade, once per voice per sample.
  - `MicroShifter.cpp:132`: the LFO, once per sample. Shipping modulation is 1.65 ms, so this runs in every shipping build.
- **Rule:** as P2-3.
- **Fix:** an incremental phasor (a rotating complex value or recurrence) for the LFO. Possibly a cheaper exact sin² for the fade, since it only needs `sin(πφ)²`. Only worth doing if a profile shows it in the top of `processBlock`.
- **Effort:** 1 h, plus a listening A/B (it changes the sound only if inexact).

### P2-5 · The lit-window layer is redrawn from scratch on every count change
- **Where:** `Skyline.cpp:124` (`rebuildLitLayer`).
- **Finding:** while sweeping, the lit count changes on almost every tick, and each rebuild clears 1.5 MB and redraws up to 211 windows and glows: 1.7% of a core in the Day 10 trace.
- **Fix:** while the count rises, draw only the newly lit windows. The order is fixed and windows are only ever added at the end, so only a falling count needs a full rebuild.
- **Caveat:** today every window is drawn before every glow, so a window added on top would cover its neighbours' glow where they overlap. Compare the result against the full rebuild, or keep windows and glows in separate layers.
- **Effort:** 30 min.

### P2-6 · No test for zipper noise while sweeping
- **Where:** `Tests/ProcessorTests.cpp`.
- **Rule:** definition of done #4: "Sweeping the knob … makes no clicks or zipper noise".
- **Finding:** smoothing is tested only for where it lands (50 → 0 nulls). Nothing checks that a fast 0 → 100 → 0 sweep on a sine has no sample-to-sample step beyond the signal's own slope, the way the bypass test does with `largestStep`.
- **Fix:** reuse `largestStep` with an automation sweep in the `render` callback.
- **Effort:** 30 min.

## P3

### P3-1 · An audio constant outside `SoundSpec.h`
- **Where:** `MicroShifter.h:58` (`maxModulationDepthMs = 3.0`).
- **Rule:** CLAUDE.md "Every audio constant is a named constexpr in Source/SoundSpec.h, with a comment linking it to its row in the PRD sound spec table".

### P3-2 · The processor does some of the mixing math itself
- **Where:** `PluginProcessor.cpp:164–210` (`renderChunk`): the wet and output gain ramps, the dry + wet mix, the mono sum, and the `GainRamp` struct.
- **Rule:** CLAUDE.md "The processor wires the parts together; it doesn't do their math."

- **Effort:** 45 min; the null and bypass tests guard it.

## Efficiency + tidiness audit

A read-only audit of main at `5d0c4c1` (Day 10, 2026-10-12), after the water shimmer merge. No code or assets were changed. Measurements used temporary copies and the existing `CpuBenchmark` host, with 1 instance at 48 kHz.

### Summary

- **Any continuous repaint with the editor open makes the host hold about 200–240 MB of graphics memory** (A2). The shimmer, and automation moving City size, both do it. It comes from JUCE's macOS renderer, not from what BigCity draws. It's steady, and it's released when the editor closes, so the shimmer ships (decided Day 10). JUCE's macOS renderer is logged for v1.1.
- **The bundle is 12.7 MB.** Two easy wins, both of which need your OK (they're build settings): stripping local symbols saves 1.85 MB (15%), measured on a copy. panel.png is stored twice, once per architecture, which is 3.0 MB.
- **Storing the keyframes at logical size isn't lossless.** The art has detail finer than one logical pixel. It would save about 14.6 MB of RAM, but only if the keyframes are redrawn.
- **Tidiness is good:**
  - no compiler warnings from BigCity's own code,
  - no unreferenced assets, sources or headers,
  - no dead functions.

  Some tokens and branches are left over.
- **Practical UI:** 5 mismatches between `docs/practical-ui.md` and what ships aren't documented there. 2 of them touch WCAG (the shimmer under 2.2.2, and D-24's missing accessibility).

### A. Efficiency

#### A1. Installed bundle size
`BigCity.vst3` is 12.7 MB on disk. The universal binary is 12.66 MB: x86_64 6.48 MB plus arm64 6.15 MB. Everything else is under 5 KB (Info.plist, moduleinfo.json, the code signature).

Embedded assets are copied into **each** architecture slice, so every asset counts twice.

| # | Contributor | Size |
|---|---|---|
| 1 | `panel.png`, ×2 slices | 2.99 MB |
| 2 | x86_64 machine code (`__text`) | 2.81 MB |
| 3 | arm64 machine code (`__text`) | 2.50 MB |
| 4 | x86_64 `__LINKEDIT` (symbol tables, signature) | 1.06 MB |
| 5 | arm64 `__LINKEDIT` | 1.03 MB |
| 6 | The 5 skyline keyframes, ×2 | 0.76 MB |
| 7 | Other `__TEXT` (strings, unwind tables, stubs), both slices | 0.33 MB |
| 8 | `__DATA` and `__DATA_CONST`, both slices | 0.25 MB |
| 9 | `knob_base.png`, ×2 | 0.18 MB |
| 10 | `screen_overlay.png`, ×2 | 0.16 MB |

- **Local symbols aren't stripped.** 12,791 of 13,660 arm64 symbols are local. `strip -x` on a copy: 12.66 → 10.81 MB (−1.85 MB, −15%). In Xcode this is `DEPLOYMENT_POSTPROCESSING`/`STRIP_INSTALLED_PRODUCT`, a build-settings change, so it needs your OK. `DEAD_CODE_STRIPPING` and LTO aren't set in the generated project either; I haven't measured those.
- **Assets total 2.14 MB per slice,** and panel.png is 70% of that.

#### A2. Memory, 1 editor open vs. closed
Measured with `footprint`, physical footprint of the whole host process, 6 s after launch:

| State | Footprint |
|---|---|
| Editor closed | 4.9 MB |
| Editor open, City size 0 (shimmer idle) | 60 MB |
| Editor open, City size 0.1 | 320 MB (242 MB of it graphics) |
| Editor open, City size 25 | 279 MB (202 MB graphics) |
| Editor open, City size 50 / 100 | 280–282 MB (203 MB graphics, 15 MB IOSurface) |
| **Pre-shimmer build (`49e975d`)**, editor open, City size 0 / 50 / 100 | 62 / 60 / 62 MB |

- **The editor itself costs about 55 MB.** That's in line with ui-spec's calculated 25.4 MB of UI images plus the window's own buffers.
- **Any continuous repaint adds about 200–240 MB of graphics memory while the editor is open.** Footprint calls it "Owned physical footprint (unmapped) (graphics)". It stays flat over time.
  - The shimmer triggers it whenever City size is above 0.
  - So does host automation moving City size, even on the pre-shimmer build: 243 MB graphics, 341 MB in all while sweeping.
  - With nothing repainting (City size 0, or the pre-shimmer build left idle) there's none.
- **It comes from JUCE's macOS renderer, not from what BigCity draws.** JUCE 8 draws through `CoreGraphicsMetalLayerRenderer` (`juce_CGMetalLayerRenderer_mac.h`). Every present copies the whole window texture on the GPU, however small the dirty area. Two follow-up tests on `fix/shimmer-memory` (not merged) changed nothing:
  - Caching the water strip, so a shimmer frame draws only two small images plus the highlights: 276–278 MB.
  - Also marking `Skyline` opaque, so the panel isn't redrawn under it: 277 MB.
- **It's released when the editor closes.** Measured on main, City size 50, with `CpuBenchmark --close-at --reopen-at`:

  | Moment | Footprint | Graphics | IOSurface |
  |---|---|---|---|
  | Editor open 60 s | 282 MB | 203 MB | 15 MB |
  | 30 s after closing | 67 MB | 2.6 MB | 10 MB |
  | Reopened, after 15 s and 33 s | 294 MB | 195 MB | 20 MB |

  After the reopen it settled 12 MB higher (IOSurface 15 → 20 MB). One cycle can't tell a small leak from caching.
- **Decision (Day 10):** keep the shimmer; the cost lasts only while the editor is open, and automation already incurred it.
- **v1.1:**
  1. Try JUCE's other macOS rendering path (`JUCE_COREGRAPHICS_RENDER_WITH_MULTIPLE_PAINT_CALLS=0`, a build-setting change), or a newer JUCE, and measure memory, CPU and looks.
  2. Run 10 open/close cycles to check the 12 MB step.
  3. Measure 2 open editors.

#### A3. What repaints, and opaque candidates
Rects are in window points.

| Component | Rect | Opaque | Knob drag | Shimmer running |
|---|---|---|---|---|

**Could be opaque but isn't:**
- **`Skyline`.** It's non-opaque only because of its 14 pt clipped corners. The water rect (rows 177–243 of 280) is clear of the corners, so the panel under it is redrawn each shimmer frame for nothing. Fixes: the skyline draws its corner pixels from the panel itself, or the shimmer gets its own opaque child for the water rect.
- **`SevenSegmentReadout`.** It could cache the panel crop behind it, as the knob does.
- **`BypassSwitch`.** It would need the same cache to cover its LED glow; low value.
- **Caveat:** P1-1 tried opaque components on Day 10 and saw no CPU gain, because most of the cost is Core Animation compositing. Making `Skyline` opaque didn't change A2's memory either (277 MB).

#### A4. Keyframes at logical size, 112 × 95 (estimate only)
- **RAM.** The 5 colour and 5 grey keyframes decode to 15.05 MB at 672 × 560. At 112 × 95 they'd be 0.43 MB, saving about **14.6 MB** per process (shared by all editors). The grey conversion at first open (P3-6) would also do 1/36 of the work.
- **Bundle.** 0.38 MB of keyframe PNGs per slice. The small versions would be roughly 0.05–0.1 MB per slice, saving about **0.6 MB** across both slices.
- **But it isn't lossless.** Only 27–40% of 6 × 6 blocks are a single colour, and even 2 × 2 blocks are only 71% uniform. Each keyframe has 1,445–3,124 colours of dither and gradient below the 3 pt grid. Storing at logical size would flatten that detail, so it would need keyframes redrawn on the logical grid, an art change.
- **No help for A2:** A2's graphics memory doesn't depend on the size of the source images.
